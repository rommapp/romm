# RomM-Themeable 2.0.5-5.4.1 Development Plan

*Screenshots on the landing page, and docs that don't publish*

Nov 8, 2026 · Stealthx3

The landing page describes the themes but shows none of them. Adding pictures touches `themeable/`, and every push to `main` that touches `themeable/` builds and publishes an image, even when only documentation changed.

## Tasks

1. **Screenshots.** `.github/README.md` opens with stock RomM's login screen next to the same screen with Phosphor, and a Screenshots section shows the ten built-in themes' login screens, the Branding tab and the `/themeable/` picker. The images are WebP files in `themeable/docs/images/`, taken through `themeable/dev/preview.mjs` from the built-in packs.
2. **Progress bar slot.** `.github/README.md` starts with a hidden slot for a one-line progress bar. It stays empty while no version is in development. `GUIDELINES.md`, "Progress bar", says when to add, update and remove the line.
3. **Docs-only pushes don't publish.** The `themeable` workflow's push trigger ignores `themeable/docs/**` and Markdown files under `themeable/`, so a change to them alone runs no build. Pull requests still run every check.
4. **Docs match the code.** An audit of the module's Markdown files against the code at this version found these, and the docs now say:
   - The pack guide's `$schema` URL points at `main` (it named a branch that doesn't exist).
   - The v1 interface gets a pack's artwork and tab icons, not only its colors.
   - Placeholder covers are drawn in code and themed with `covers`; `/assets/default/` holds the avatar, not covers.
   - The 20 MB upload cap is listed with the archive limits, and the archive limits are worded exactly: entries count folders, and the ratio is for the whole archive.
   - An upload takes its id from `theme.json`; a pack copied in by hand must be named `<id>.zip`, and one with a built-in id replaces that pack, while an upload can't.
   - The rules for ids, names, tags, cover image types, platform icon types and SVG content are complete.
   - Folder packs are converted at start-up or the next recompile, not only when the container starts.
   - Zipping on Windows is described through File Explorer only.
   - `themeable/README.md` drops a stray versioning note, describes when the `themeable` workflow runs, and does a manual adoption on a `release/<version>` branch merged with approval, rather than on `main` or on the workflow's `themeable-upstream/<tag>` branch.
   - Repository setup lists enabling issues and protecting `main`, from 2.0.2.
   - Image-tag and version examples use the current release.
   - `GUIDELINES.md` says where the reserved ids live and that the repository, not the Project, holds every plan.

5. **A lab for instructions.** The `themeable-lab` agent (`.claude/agents/themeable-lab.md`) runs `themeable/test/doc-checks/plan.md` in a libvirt VM on the owner's host. Each check runs the published instruction and its replacement, and every change in task 4 passed there before it was kept. Windows isn't tested: romm-themeable is a web app with no Windows build.

## Version

`themeable/package.json` becomes `2.0.5`. This release changes the `themeable` workflow, so its merge into `main` builds and publishes an image like any other release.

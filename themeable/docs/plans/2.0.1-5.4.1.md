# RomM-Themeable 2.0.1-5.4.1 Development Plan

*Verifying what gets published*

Oct 23, 2026 · Stealthx3

Upstream adoptions keep merging by themselves (`THEMEABLE_AUTO_MERGE` stays on), so every published image is now checked after it is pushed, and a failure opens an issue instead of passing unnoticed.

## Tasks

1. **Follow-up verification.** A `verify` job runs after the image job on `main`. It checks that the `:<ROMM_VERSION>`, `:<module>-<ROMM_VERSION>` and `:latest` tags all point at the build just pushed, for amd64 and arm64. It then deploys that image with the root `docker-compose.yml` through `scripts/verify-deployment.mjs` and checks RomM's health and version, the module version inside the image, the start-up compile, the loader, the theme stylesheets and artwork, the `/themes/` sandbox headers, and a start-up log without errors. A failure opens an issue with the run's link.
2. **Release tags.** Images are also tagged `:<module>-<ROMM_VERSION>` (for example `:2.0.1-5.4.1`), which never moves, and carry `org.opencontainers.image.version`.
3. **Compose file.** The root `docker-compose.yml` describes the themes folder as `.zip` packs, lists `THEMEABLE_MAX_UPLOAD_MB`, and names the image tags. Because the verification deploys with this file, it is tested on every build.
4. **Schedule.** After this release is on `main`, the `themeable upstream release` workflow is run by hand so the hourly adoption is confirmed working with the changes since 5.4.1 (the major-version bump, the report wording and the action pins).

# RomM-Themeable 1.1.0-5.4.0 Development Plan

*Random Theme, Pack Archives, Uploads, and Refinement of Built-ins*

Oct 17, 2026 · revised Oct 21, 2026 · Stealthx3

Four phases of work on the themeable module: a random-theme option, packs stored as .zip archives, uploading, renaming and deleting packs from Branding, and a refinement pass over the built-in themes. Per-user themes, permissions and public or private packs have moved to a follow-up release; see **Deferred to the follow-up release** at the end.

## At a glance

The work splits into four phases, built strictly in this order. Random theme comes first as the smallest self-contained change. Archives come before uploads because an upload is an archive. Refining the built-in themes comes last: it changes how the packs look, not how the module works, and its scope is settled collaboratively as the work goes.

| Phase | Feature (your item) | What changes | Depends on |
|---|---|---|---|
| A | Random theme option | A **Random** option heads the Branding list; each page load picks a pack at random, and its preview cycles through all available packs’ existing artwork every 2 seconds | none |
| B | The packs are now .zip archives | A pack is one `<id>.zip` in the themes folder; the compiler reads it without unpacking it onto disk | none |
| C | Web upload, delete and rename functionality | An upload control at the top of Branding takes a .zip, checks it and installs it; uploaded packs can be renamed and deleted; RomM default can be neither, and built-ins can only be hidden; administrators only | B |
| D | Refine existing built-in themes | Make animated backgrounds loop cleanly, make the artwork more interesting, and add accessibility-focused themes for visually impaired users; open-ended and collaborative | none |

**Process improvements:**

**Branch.** All work for this release happens on a development branch, `release/1.1.0-5.4.0`, created from `main`. The linked local folder, currently on `main`, becomes the working copy for that branch. On that branch only, `themeable/package.json` is set to version `1.1.0`.

**Commits.** Changes are committed locally as they are made, in small commits. Nothing is pushed while a phase is in progress.

**Pushes.** A phase is complete once its unit tests, visual check and patched-source check pass and its README and guide updates are done. Its commits are then pushed to `release/1.1.0-5.4.0`, but only after the owner approves the push. The push reruns the tests, source check and visual check on the branch; it never builds an image.

**Workflow change (first commit on the branch).** `themeable.yml` runs only for `main` today, and every push there builds and publishes `ghcr.io/stealthx3/romm-themeable:5.4.0` and `:latest`. Its push trigger gains `release/**` so the test, source and visual jobs run on the development branch, and the image job gets the guard `github.ref == 'refs/heads/main'` so nothing is published from it.

**Container builds.** No image is built or published until all four phases are complete. Then, with the owner's approval, the branch is merged into `main`, which runs the image job: build, smoke test and publish.

**Handoff.** How commits are made in the local folder (branch creation and the git tooling available to the implementing session) is settled when this plan is handed to Claude Code. These process rules apply to every release; see [`themeable/GUIDELINES.md`](../../GUIDELINES.md).

## Phase A: random theme

A new option, **Random**, sits at the very top of the Branding list, above **RomM default**. When it is the server's theme, every page load shows a pack picked at random from the usable packs.

**Choosing the theme**

- `random` becomes a reserved id beside `none` and `default`, published to the browser files through the shared values in `lib/client.mjs`.
- The loader resolves `random` before the page renders: it picks uniformly from the usable packs in the manifest (built-in packs that haven't been hidden, and uploaded packs that compiled), avoiding the pack this browser showed last time when more than one exists, then sets the theme attribute, stylesheet and artwork cookie exactly as for a fixed choice. One pick holds for the whole page load, so artwork and colors always match.
- RomM default is left out of the draw, since it is “no theme”.
- Browser tab icons come from the server's theme today. With Random they follow the theme each visitor was dealt instead, by having nginx read the visitor's theme cookie for tab icons too.

**The cycling preview**

- The Random entry's artwork strip shows one usable pack at a time and switches to a different, randomly chosen pack every 2 seconds. All four tiles (login background with logo, wordmark on dark and on light, tab icon) change together, so each step shows one real pack.
- Images for the next pack load before the switch, and the change is a short cross-fade, so the strip never flashes empty.
- The cycle pauses while the tab is hidden and does not run for visitors with reduced motion turned on; they see one pack, with the pack's name shown under the strip.
- With only one usable pack, the strip shows it without cycling; with none, Random is disabled with the reason.

**Also updated:** the `/themeable/` picker gets a Random card, Branding's Preview for Random opens a random pack, and tests cover the draw (seeded), the reserved id, and the cycling component's timer and pause behavior.

## Phase B: pack archives

A pack becomes a single file, `themes/<id>.zip`, with `theme.json` at the archive's root (or inside one top-level folder, which is how most zip tools package a folder). The compiler reads every file straight out of the archive; nothing is unpacked into the themes folder.

```
themes/
  themeable.json      ← settings: server theme, hidden built-in packs
  midnight.zip        ← one pack per archive, file name = pack id
  neon-custom.zip
```

**How it works**

- A new `lib/zip.mjs` reads a zip's central directory and inflates entries with Node's built-in `zlib`, so the module still needs no dependencies. It supports stored and deflated entries, the two methods every common zip tool writes, and refuses encrypted, multi-disk and other methods with a clear error.
- `collectPacks` lists `*.zip` instead of folders and gives the validator and compiler a small "pack source" interface (`list`, `read`, `exists`) in place of file paths. Validation stays the same: paths must stay inside the pack, extensions must match, files must exist.
- The compiler copies each replacement file from the archive into the compiled build, as it copies from folders today. Archives are opened once per compile, and a compile only rereads an archive whose size or modification time changed.
- Limits checked before anything is inflated: at most 2,000 entries, 64 MB uncompressed in total, 16 MB per file, and a compression ratio no higher than 100:1. Each limit is a named constant and an environment variable.

**Built-in packs** stay as folders in the repository, where they are easy to edit and review, and the image build zips them into `/themeable/packs/*.zip`, so the compiler only ever reads archives.

**Moving existing folder packs over.** Folder packs in the themes folder keep working for this release, marked **Folder pack: convert to .zip** in Branding with a one-click **Convert** that writes `<id>.zip` and moves the folder to `themes/.converted/<id>/`. The follow-up release drops folder support.

**Also updated:** the pack guide and illustrated guide (zip instead of folder, how to zip a pack on Windows, macOS and Linux), the local preview's `--packs-folder`, the visual check, and tests for every limit and for malformed archives (truncated, zip-slip paths, duplicate names, a nested zip).

## Phase C: web upload

Branding is the administrators' space for themes and is treated as authoritative: it lists every pack on the server and is where packs are uploaded, renamed and deleted. An **Upload a theme pack** control sits at the very top of Branding, above the theme list. Branding, and every action in this phase, stays administrator-only in this release.

**Flow.**

1. The user picks or drops a `.zip`. The page checks the extension and size before sending, so obvious mistakes fail instantly.
2. `POST /api/themeable/packs` receives it as a multipart upload, streamed to a temporary file with a hard size cap (20 MB by default, set by `THEMEABLE_MAX_UPLOAD_MB`). Anything larger is cut off and refused with 413.
3. The backend hands the file to the runtime script's new `validate-archive` command, which runs the same archive reader and validator as Phase B: entry limits, path checks, `theme.json` schema, asset types and sizes. Nothing is written to the themes folder yet.
4. If validation fails, the response lists the problems in the same wording the Branding diagnostics use, and the temporary file is deleted.
5. If it passes, the archive is moved into the themes folder as `<id>.zip` with an atomic rename, and the usual compile runs under the existing lock, timeout and stop-on-cancel handling. A failed compile restores the previous archive, if there was one, so a bad upload never leaves the server worse off.
6. The new pack appears in the list with its artwork preview, ready to choose.

**Id clashes.** The pack id comes from `theme.json`, not the file name. Uploading an id that already exists replaces that uploaded pack once the administrator confirms. Built-in packs can't be replaced by upload; to change one, upload it under a new id.

**Managing packs: rename and delete.** Packs get **Rename** and **Delete** actions in Branding. RomM default never gets either, and the backend refuses both for it whatever the page sends. Built-in packs can't be renamed, but administrators can delete them.

- **Rename** changes the pack's display name. The runtime script rewrites the name in the archive's `theme.json` into a new archive, validates it, swaps it in with an atomic rename and recompiles, so a failure leaves the original untouched. The pack id stays the same, so the server theme, browsers' picker choices and preview links keep working.
- **Delete** removes the archive and recompiles, after Branding asks for confirmation. If the deleted pack was the server theme, the server falls back to RomM default, and browsers that had picked it in the `/themeable/` picker fall back to the server theme. Deleting a built-in pack hides it server-wide rather than removing it from the image: it stays hidden across upgrades, and Branding's **Restore built-in packs** action brings it back.
- Both go through `PATCH` and `DELETE /api/themeable/packs/{id}` and run under the existing compile lock.

## Phase D: refining the built-in themes

This phase improves form, not function, and is deliberately open-ended: what changes is decided together while the work is under way. The lists below are starting points, not commitments.

**Motion**

- Check every animated login background for a clean loop: the last frame matches the first, layered animations share a common period, and nothing jumps when the cycle restarts.
- Keep motion slow and low in contrast so it sits behind the login form; the still versions keep serving Firefox and reduced-motion visitors.

**Artwork**

- Give each pack's background more depth (layering, soft glow or grain, gentle parallax) while keeping the pack's idea and palette.
- Fill gaps: Ember ships no browser tab icons and has the simplest background of the set.
- Where the catalog allows, add placeholder cover art and platform or provider icons per pack, so a pack restyles more than the login screen.
- Check that logos and wordmarks read well in both light and dark mode.

**Accessibility themes**

- High Contrast Dark and High Contrast Light, aiming at WCAG AAA contrast (7:1) for body text.
- A pack that never relies on red versus green alone to show state.
- For all of them: still backgrounds only and stronger focus outlines, with a larger base text size and spacing as an option to explore.

**Possible new packs**

- A light-first pack, and a minimal pack with no background artwork for low-power devices and TVs.

**Also updated:** the visual check's reference images, the README's list of built-in themes, and the pack guide wherever a built-in pack is used as an example.

## Deferred to the follow-up release

These were part of the original request and move to the next release, together with anything else from the original request not covered above:

- Per-user themes and the User Theme section, including Random there and uploads by users who aren't administrators.
- Permissions in RomM's permission groups (switching the theme for oneself or for everyone, managing packs) and the rename and delete rules that follow from them.
- Public and private packs, including the warning shown when a private pack is applied as the server theme.
- The theme audit log (`themeable-audit.log`) and its view in Branding.
- Dropping support for folder packs.
